## Scope — read this carefully

This task covers the **file header, the chunks, and the event-record framing
only**.

**Do not implement BinXML.** The payload inside each record is binary XML with
templates and substitution arrays; it is a large separate job and is the next
task. Here you record the payload's length and move on.

That still has real value: it yields a timeline of record identifiers and
timestamps, and it proves the chunk walking works before BinXML is layered on.

An `.evtx` file reaches hundreds of megabytes, so **stream it**: read the file
header, then each 65536-byte chunk one at a time through `reader.bytes()`.
Never read the whole file into memory.

## Format — [EVTX], libevtx documentation

### File header, 4096 bytes at offset 0

| Offset | Type | Meaning |
|---|---|---|
| 0 | 8 bytes | signature, ASCII `ElfFile\0` |
| 8 | u64 | first chunk number |
| 16 | u64 | last chunk number |
| 24 | u64 | next record identifier |
| 32 | u32 | header size, 128 |
| 36 | u16 | minor version, 1 |
| 38 | u16 | major version, 3 |
| 40 | u16 | header block size, 4096 |
| 42 | u16 | number of chunks |
| 120 | u32 | file flags: bit 0 dirty, bit 1 full |
| 124 | u32 | CRC-32 of bytes 0..119 |

The whole header block is 4096 bytes; the first chunk starts at 4096.

**Do not trust `number of chunks`.** A dirty log can understate it. Walk chunks
until the file ends or a chunk's signature does not match, and warn if the count
you find differs from the header's.

### Chunk, 65536 bytes, first one at offset 4096

| Offset | Type | Meaning |
|---|---|---|
| 0 | 8 bytes | signature, ASCII `ElfChnk\0` |
| 8 | u64 | first event record number |
| 16 | u64 | last event record number |
| 24 | u64 | first event record identifier |
| 32 | u64 | last event record identifier |
| 40 | u32 | header size, 128 |
| 44 | u32 | offset of the last record, relative to the chunk start |
| 48 | u32 | free space offset, relative to the chunk start |
| 52 | u32 | CRC-32 of the event-record data |
| 124 | u32 | CRC-32 of bytes 0..119 plus bytes 128..511 |

Bytes 128..383 are a common-string offset table and 384..511 a template table.
Both are for BinXML, so **skip them**. Event records begin at chunk offset
**512** and run until the free space offset.

### Event record

| Offset | Type | Meaning |
|---|---|---|
| 0 | u32 | signature, `0x00002a2a` |
| 4 | u32 | record size, including this header and the trailing copy |
| 8 | u64 | event record identifier |
| 16 | FILETIME | written time |
| 24 | size-28 bytes | BinXML payload — **record its length, do not parse it** |
| size-4 | u32 | copy of the record size |

Walk records from chunk offset 512 while the offset is below the free space
offset. A record whose signature is wrong, whose size is below 28, or whose
size would run past the chunk end is corrupt: `ctx.warn()` and **stop walking
that chunk**, then continue with the next chunk. One bad chunk must never cost
the records in the others.

Verify the trailing size copy matches the leading size; warn when it does not,
but still emit the record.

## Required output columns — exact keys, one row per event record

```
recordId     num   event record identifier
writtenTime  date
chunkNumber  num   zero-based index of the chunk it came from
recordSize   num   the record size field
dataLength   num   payload length, i.e. recordSize - 28
offset       num   absolute byte offset of the record in the file
```

## sniff()

True when the first 8 bytes are `ElfFile\0`. `extensions: ['.evtx']`.

## Behaviour on bad data

Never throw. Warn and continue. Specifically:

- A bad file signature: warn and emit nothing.
- A chunk whose signature is wrong: warn, skip that chunk, keep going.
- A truncated final chunk: parse the records that fit, then warn.
- A free space offset beyond the chunk: warn and fall back to the chunk end.

Do not verify CRC-32 values in this task. Reading them is fine; failing on them
is not, because a dirty log has stale checksums and must still be parsed.

## Tests

`fixtures/evtx/Synthetic.evtx` is generated by `fixtures/evtx/make.mjs` from the
layout above, independently of any parser. `expected.json` maps the filename to
the exact rows your parser must produce.

Read it with `node:fs`, wrap with `bufReader` from `src/core/reader.ts`, drive
through `run()` from `src/core/registry.ts`, and deep-compare with Date fields
converted via `.toISOString()`.

`expected.json` is the specification. If your parser disagrees with it, your
parser is wrong — never edit the fixture or the expected file to make a test
pass.

Also add:

- **truncation**: parse `buf.subarray(0, n)` for n = 100, 4096, 5000 and half
  the length. Assert it never throws and never hangs. At n = 4096 there are no
  chunks at all, which must produce zero rows and a warning, not a crash.
- **garbage**: 70000 random bytes with `ElfFile\0` written at offset 0. Assert
  no throw and no hang.

Finally run `npm run typecheck` and `npm test` and report the real output.
