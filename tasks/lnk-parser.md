## Scope

Parse the header, the LinkInfo block, the string data and the TrackerDataBlock.

**Do not parse the shell-item ID list in this task.** It is shared with
ShellBags and is a separate piece of work; just read its size and skip over it.

## Format — [MS-SHLLINK]

### ShellLinkHeader, 76 bytes, at offset 0

| Offset | Type | Meaning |
|---|---|---|
| 0 | u32 | HeaderSize, always `0x4C` |
| 4 | 16 bytes | LinkCLSID, always `00021401-0000-0000-C000-000000000046` |
| 20 | u32 | LinkFlags |
| 24 | u32 | FileAttributes |
| 28 | FILETIME | target creation time |
| 36 | FILETIME | target access time |
| 44 | FILETIME | target write time |
| 52 | u32 | target file size |
| 56 | i32 | icon index |
| 60 | u32 | ShowCommand |
| 64 | u16 | hotkey |
| 66 | 10 bytes | reserved |

LinkFlags bits: `0x01` HasLinkTargetIDList, `0x02` HasLinkInfo, `0x04` HasName,
`0x08` HasRelativePath, `0x10` HasWorkingDir, `0x20` HasArguments, `0x40`
HasIconLocation, `0x80` IsUnicode.

### After the header

If HasLinkTargetIDList: a `u16` size, then that many bytes of ID list. **Skip
it.**

If HasLinkInfo, a LinkInfo block starts here. All its offsets are relative to
the **start of the LinkInfo block**:

| Offset | Type | Meaning |
|---|---|---|
| 0 | u32 | LinkInfoSize |
| 4 | u32 | LinkInfoHeaderSize |
| 8 | u32 | LinkInfoFlags: `0x1` VolumeIDAndLocalBasePath, `0x2` CommonNetworkRelativeLink |
| 12 | u32 | VolumeIDOffset |
| 16 | u32 | LocalBasePathOffset |
| 20 | u32 | CommonNetworkRelativeLinkOffset |
| 24 | u32 | CommonPathSuffixOffset |

LocalBasePath and CommonPathSuffix are NUL-terminated single-byte strings.
`targetPath` is LocalBasePath concatenated with CommonPathSuffix.

VolumeID, at LinkInfo + VolumeIDOffset:

| Offset | Type | Meaning |
|---|---|---|
| 0 | u32 | VolumeIDSize |
| 4 | u32 | DriveType |
| 8 | u32 | DriveSerialNumber |
| 12 | u32 | VolumeLabelOffset, relative to the VolumeID start |

DriveType: 0 Unknown, 1 No root directory, 2 Removable, 3 Fixed, 4 Remote,
5 CD-ROM, 6 RAM disk. Emit the word, e.g. `"Fixed"`.

### StringData, immediately after LinkInfo

Present only when the matching LinkFlag is set, and **always in this order**:
NAME, RELATIVE_PATH, WORKING_DIR, ARGUMENTS, ICON_LOCATION.

Each is a `u16` character count followed by that many characters — UTF-16LE when
the IsUnicode flag is set, otherwise single-byte. The count is in
**characters, not bytes**.

### ExtraData blocks, after StringData

Each block is a `u32` size then a `u32` signature. A size below 4 terminates the
list. The one needed here is TrackerDataBlock, signature `0xA0000003`, whose
MachineID is 16 single-byte characters at offset 16 within the block, NUL
padded.

## Required output columns — exact keys, one row per .lnk file

```
targetPath        str   LocalBasePath + CommonPathSuffix
arguments         str
workingDirectory  str
description       str   the NAME string
iconLocation      str
targetSize        num
targetCreated     date
targetModified    date   the WRITE time
targetAccessed    date
driveType         str    the word, e.g. "Fixed"
driveSerial       str    8 uppercase hex digits, zero padded, no "0x"
volumeLabel       str
machineId         str    from TrackerDataBlock, or null
offset            num    always 0
```

A string that is absent because its flag is clear must be `null`, not `""`.
The one exception is `volumeLabel`, which is `""` when the volume genuinely has
an empty label.

## sniff()

True when the first 4 bytes are `0x4C 0x00 0x00 0x00` **and** bytes 4..19 are
the LinkCLSID above. Both checks are required — `0x4C` alone is far too weak.
`extensions: ['.lnk']`.

## Behaviour on bad data

Never throw. Use `ctx.warn(offset, message)` and keep going. A truncated
LinkInfo must still yield a row carrying the header fields. An offset pointing
past the end of the buffer means: warn, leave that column null, continue.

## Tests

`fixtures/lnk/notepad.lnk` is a **real shortcut generated by Windows itself**
via `WScript.Shell`, so the byte layout is authoritative. `expected.json` maps
the filename to the exact row your parser must produce; its values are what was
requested when the shortcut was created, so they are independent ground truth.

Read the fixture with `node:fs`, wrap it with `bufReader` from
`src/core/reader.ts`, drive it through `run()` from `src/core/registry.ts`, and
deep-compare with Date fields converted via `.toISOString()`.

`expected.json` is the specification. If your parser disagrees with it, your
parser is wrong — do not edit the fixture or the expected file to make a test
pass.

Also add:

- **truncation**: parse `buf.subarray(0, n)` for n = 20, 76, 200 and half the
  length. Assert it never throws and never hangs.
- **garbage**: 4096 random bytes with a valid header size and CLSID written in.
  Assert no throw.

Finally run `npm run typecheck` and `npm test` and report the real output.
